# Technical Video Production

## Project intent

Create informational, conversational technical videos that make a complex concept understandable without stripping away the mechanism that makes it work. Treat the viewer as a capable technical peer who is new to this particular subject.

The intended experience is a knowledgeable colleague explaining a system clearly, with a polished presenter-led production and graphics that carry part of the explanation. The viewer should finish able to describe how the system works, interpret relevant evidence, and apply the idea.

Apply this skill to the requested script, outline, storyboard, production plan, or review. Do not automatically generate a full production package when only one deliverable is requested. Explicit user directions take precedence over these defaults.

## Audience and teaching approach

Start each assignment by identifying the viewer's likely prerequisites and one learning outcome: "After watching, the viewer can explain or do ..."

- Assume technical curiosity and general competence, not familiarity with every subsystem.
- Begin with an observable problem or familiar behavior. Explain why the mechanism matters before introducing its terminology.
- Build from a simple model to the realistic system. Introduce a component when it answers a question the viewer already has.
- Follow one concrete example through the explanation. Show what enters, what changes, what leaves, and what happens next.
- Distinguish a useful simplified model from actual implementation. Name the omitted detail when it would change the viewer's conclusion.
- End with an operational takeaway: what to inspect, measure, compare, or try.

Use an analogy only when it makes the mechanism clearer. Map the analogy back to the actual components and state where it stops being accurate. Keep the technical explanation intact after removing the analogy.

## Script voice

Write for speech: direct, clear, curious, and calmly authoritative.

- Address one viewer with "you." Use "we" when walking through a shared example.
- Prefer contractions, concrete verbs, and short clauses. Vary sentence length enough to sound natural.
- Use a real question to move the explanation forward: "What changes when a second request arrives?" Answer it promptly.
- Let transitions carry logic: "That handles one request. Now let's add another." Avoid a succession of unrelated facts.
- Define necessary terms at first use, then use the same name consistently. Expand an acronym when it helps comprehension.
- Explain causality explicitly: what changes, why it changes, and what the viewer should notice.
- Make claims at the strength the evidence supports. Attach qualifications to the claim they limit.

Avoid brochure language, exaggerated promises, unexplained acronym chains, forced humor, and lines such as "obviously," "it's trivial," or "as everyone knows." Conversational does not mean vague, imprecise, or padded with filler.

Default to one presenter who anticipates the viewer's questions. Use multiple speakers only when requested or when the format benefits from an actual exchange.

## Narrative structure

Adapt this sequence to the topic and requested duration. It is a teaching pattern, not a mandatory chapter count.

1. **Recognizable situation and stakes.** Start with a concrete behavior, question, or friction point. Establish what the viewer will understand.
2. **Smallest useful mental model.** Identify the few components needed to explain the first step.
3. **Mechanism in motion.** Trace one example through those components. Show intermediate states and feedback loops.
4. **A meaningful complication.** Add the condition that exposes the simple model's limits: scale, waiting, failure, context, contention, or coordination.
5. **Evidence and interpretation.** Explain what a demonstration or measurement actually tests before showing the result.
6. **Practical synthesis.** Reassemble the system and answer the opening question. Offer a relevant next step or resource.

When evidence is central, explain the metric before celebrating the number. When a concept does not need benchmarks, use a worked example or observable behavior instead.

Avoid a long biography, agenda, or branded preamble before providing value. Introduce product names when their role is understandable, and explain the role before listing features.

## Pacing and script-to-screen design

If duration is unspecified, use roughly 5–8 minutes as a starting assumption for one focused concept. Adjust for scope and viewer prerequisites. This is a project default, not a measured runtime target from the reference.

Estimate narration at roughly 130–155 words per minute, then add time for diagrams, demonstrations, and deliberate pauses. Confirm duration with a read-through; do not equate word count with final runtime.

For each explanatory beat:

- State one question or teaching point.
- Write the spoken explanation.
- Identify the visual that makes it easier to understand.
- Specify what changes on screen and when the viewer should look at it.
- Allow enough time to read the labels or follow the state change.

Let complexity determine the pace. Slow down when introducing a new mechanism; move faster when applying a familiar one. Change the visual at a conceptual transition rather than on a fixed cut timer.

## Visual production direction

Use the reference's restrained presenter-and-diagram approach as the baseline, while adapting colors and branding to the project.

### Presenter

- Favor uncluttered composition, a subdued background, controlled lighting, and clear separation between the presenter and the background.
- Frame so expressions and purposeful hand gestures remain visible. Keep eyeline, exposure, skin tones, and white balance consistent across shots.
- Use a closer composition when emphasis warrants it. Do not assume the reference's exact camera setup or equipment.
- Keep lower thirds concise and brief. Reserve room for captions and explanatory overlays.
- Return to the presenter when a human explanation helps connect ideas; use graphics when the viewer needs to inspect structure or behavior.

### Diagrams, demonstrations, and motion

- Use a limited palette, consistent type hierarchy, and stable positions for recurring components.
- Reveal the system in the same order as the narration. Highlight the active component, path, or state.
- Show directional flow, dependencies, loops, and waiting explicitly when relevant.
- Make motion communicate a change: work arriving, data moving, a queue growing, or a result returning.
- Preserve orientation between shots. Avoid redrawing the entire system when only one part changes.
- Use screen capture or code only when it teaches something the viewer needs. Crop to the relevant area and enlarge the active line or control.
- Prefer explanatory graphics over generic technology stock footage. Do not use decoration to fill a gap in the explanation.

### Text, charts, and accessibility

- Keep on-screen text to key terms, short statements, labels, and necessary qualifications. Avoid duplicating full narration paragraphs.
- Test diagrams and charts at the intended playback size. Small labels in the reference previews are a reason to check legibility, not a reason to copy their size.
- Introduce axes, units, workload, and comparison conditions before asking viewers to interpret a result.
- Distinguish illustrative quantities from measured data. Do not turn a hypothetical example into a benchmark claim.
- Use labels or shapes alongside color. Keep captions clear of important information.
- Match caption spelling to technical names, symbols, and acronyms.

## Editing and sound standards

These are proposed production standards; the reference's audio and editing could not be evaluated.

- Prioritize intelligible, consistent speech with minimal room noise, distracting reverb, clipping, or abrupt level changes.
- Use music sparingly, if at all, beneath dense explanations. Sound effects should support meaningful actions without competing with speech.
- Cut for clarity and thought boundaries. Retain pauses that allow a diagram or important claim to register.
- Align narration with the corresponding visual state. Avoid showing the next mechanism while the presenter is still explaining the previous one.
- Keep transitions restrained and the visual vocabulary consistent.
- Review the assembled video with audio, then check graphics at realistic viewing size. A script review alone cannot validate the finished production.

## Technical credibility

For scripts containing factual claims:

- Consult current primary sources for version-sensitive behavior, specifications, and performance claims.
- Keep source links and assumptions in production notes, separate from spoken narration unless attribution helps the viewer.
- Explain the test or example's boundaries. Do not generalize a result beyond its workload or conditions.
- For comparisons, retain the relevant hardware, software, precision, concurrency, latency target, and measurement units.
- Separate what was measured, the proposed explanation, and any prediction.
- Mark unresolved claims clearly and resolve or remove them before calling the script production-ready.

Do not reuse the reference video's numerical results as defaults for another topic or episode. Its visual style is reusable; its technical claims require their own verification.

## Deliverable conventions

For a script-only request, deliver speakable narration with concise visual cues and any necessary source notes. For a production-ready script or storyboard, organize scenes with:

- **Purpose:** What the viewer should understand.
- **Narration:** The exact spoken words.
- **Visual:** Presenter, diagram, chart, code, or demonstration.
- **Action:** The reveal, highlight, movement, or cut tied to narration.
- **Timing:** An estimated duration, including reading and demonstration time.
- **Evidence:** Sources, assumptions, and unresolved claims where applicable.

Use the project's established format if one exists. Do not add shoot schedules, equipment lists, or distribution plans unless requested.

### Original style example

The following is an original illustration of the target style, not a quotation or reconstruction of the reference.

**Purpose:** Explain how a shared resource can introduce waiting.

**Narration:** "One request arrives, and the worker starts processing it. Now a second request arrives while the worker is still busy. In this simplified system, that request has to wait. So the time a user experiences includes both the wait and the work. If we measure only processing time, we miss part of the experience."

**Visual:** A request enters a worker. A second request joins a visible queue. A timeline separates waiting from processing.

**Action:** Reveal the second request when it is mentioned. Extend the waiting segment before showing the processing segment.

**Evidence note:** This deliberately simplified example assumes one worker that handles one request at a time. Label the assumption; real systems can schedule work differently.

## Review before delivery

Check the requested artifact against these criteria:

- The opening gives a technical viewer a concrete reason to continue.
- The explanation builds on defined concepts and follows a coherent example.
- The viewer can explain the mechanism, not merely repeat the terminology.
- Narration sounds natural when read aloud and answers likely questions.
- Visuals explain relationships or behavior and stay synchronized with the script.
- Necessary labels and qualifications remain readable.
- Technical claims have appropriate evidence and scope.
- Duration includes time for comprehension, not just speech.
- The ending resolves the opening question and provides a useful next step.

For review requests, identify specific problems, their effect on comprehension, and a concrete revision. Distinguish flaws observed in the supplied artifact from production risks that still need checking. Never claim to have watched or heard material that was unavailable.
